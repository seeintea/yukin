# Yukin Agent Run 前后端交互计划

> 创建时间：2026-08-18 20:51:33（Asia/Shanghai）
>
> 状态：阶段 1、阶段 2 已实施
>
> 关联计划：`2026-08-13_133430-通用桌面助手-v1-开发计划.md`
>
> 目标：将当前单轮模型流升级为可持久化、可取消、可扩展 Tools 与 Skills 的真实 Agent 交互链路。

## 1. 当前状态

当前已经完成可持久化、可取消、可恢复的多轮文本链路：

```text
React 输入
  → agent_run_start 创建持久记录并立即返回 IDs
  → 后台 Agent Run 调用 provider adapter
  → 版本化 Run Event + Tauri Channel
  → React reducer + React Query + Streamdown
  → Snapshot 恢复与最终持久状态校准
```

当前能力：

- 可以创建、切换和恢复多轮 Conversation。
- Message 和 Run 会保存状态、模型配置、部分输出和 Token Usage。
- Command 创建后台 Run 后立即返回 IDs，运行可以取消。
- Run Event 带版本、ID、Run sequence 和时间戳，前端按序去重。
- 事件丢失或页面重载后可以通过 Snapshot 恢复活动 Run。
- 应用启动时会将遗留活动 Run 标记为中断失败。
- Rust 区分隐藏推理与最终文本，只向前端发送阶段和最终文本。

当前限制：

- 一次 Run 仍只调用一次模型，不存在 Agent Loop。
- 没有 Tool Call、审批和 Skills。
- 尚未实现步骤上限、工具超时和工具输出限制。

## 2. 已确认的设计决策

1. Rust 是 Conversation、Message、Run、Tool Call 和权限状态的权威来源。
2. React 只保存输入框、菜单和当前动画等临时界面状态。
3. 一次用户提交对应一个 Run；Run 可以包含多次模型请求和多次工具调用。
4. 模型供应商适配器只处理供应商协议，不负责数据库、Skills、工具审批或业务流程。
5. Tools 只在 Rust 执行；前端不能根据模型文本自行执行系统能力。
6. Skills 在 Run 启动时由 Rust 解析，用于形成指令和可用工具集合。
7. 隐藏推理不发送给前端，也不默认持久化；前端只接收 `thinking` 阶段状态。
8. 流式增量用于即时显示，持久状态通过快照恢复，暂不持久化每个 Token Event。
9. 先完成真实多轮对话，再实现工具，最后接入 Skills，不提前创建空模块。
10. 第一版不要求恢复应用退出时正在执行的 Run；重启后可以将其标记为失败或中断。

## 3. 职责边界

### Commands

- 只接收 IPC 请求、获取应用状态、调用 Workflow 并返回协议类型。
- 不执行 SQL、不直接调用供应商、不编排 Agent Loop。

### Workflows

- 负责 Conversation 和 Run 的完整业务顺序。
- 组合 Storage、Agent Runtime、Tools、权限和系统能力。
- 负责事务边界、状态转换、取消和错误收口。

### Agent Runtime

- 负责模型调用循环、上下文组装和模型工具调用处理。
- 维护同一 Run 内需要继续回传给模型的临时推理状态。
- 输出与供应商无关的结构化 Agent Event。

### Provider Adapter

- 将内部 Agent Request 转换为 OpenAI、Anthropic 等供应商请求。
- 将供应商流转换为文本、推理、Tool Call 和完成事件。
- 不感知数据库实体、审批弹窗和 Skill UI。

### Storage

- 只负责 SQLite、SQLx 查询、记录映射和 Migration。
- 不包含 Run 执行顺序和 Agent Loop。

### React

- 展示会话、消息、流式文本、运行阶段、Tool Call 和审批请求。
- 调用 Commands 提交用户选择，不自行推断后端状态。
- 事件丢失或窗口重载后，通过快照重新加载权威状态。

## 4. 核心领域模型

### Conversation

表示一组连续的多轮交互。

```text
id
title
created_at
updated_at
```

### Message

表示发送给模型或由模型生成的一条消息。第一阶段只支持文本，不提前抽象通用 Message Part。

```text
id
conversation_id
run_id nullable
role                 user | assistant | tool
content
status               streaming | completed | failed | cancelled
sequence
created_at
updated_at
```

约束：

- Conversation 内 `sequence` 单调递增。
- 用户消息创建后即为 `completed`。
- 助手消息在 Run 开始时创建为 `streaming`，结束时更新最终状态。
- Tool Result 后续可以使用 `tool` role，并通过 Tool Call ID 关联。

### Run

表示一次用户提交触发的完整 Agent 执行。

```text
id
conversation_id
provider_id
model_id
reasoning_effort nullable
status               pending | running | waiting_approval |
                     completed | failed | cancelled
error_code nullable
error_message nullable
prompt_tokens nullable
completion_tokens nullable
total_tokens nullable
created_at
started_at nullable
completed_at nullable
```

模型和推理配置记录在 Run 上，保证历史消息可以知道当时使用的配置；API Key 不进入 Run。

### ToolCall

在接入第一个工具时再创建对应表和模块。

```text
id
run_id
name
arguments_json
result_json nullable
status               requested | waiting_approval | running |
                     completed | failed | rejected | cancelled
risk_level
error_code nullable
error_message nullable
created_at
completed_at nullable
```

## 5. Run IPC 协议

### 启动请求

```ts
interface AgentRunStartRequest {
  conversationId: string;
  providerId: string;
  modelId: string;
  reasoningEffort: ReasoningEffort | null;
  content: string;
  skillIds: string[];
}
```

第一阶段尚未接入 Skills 时，`skillIds` 可以暂不加入实际协议；接入 Skills 时再新增，不为未来字段创建无效实现。

### 启动响应

```ts
interface AgentRunStartResponse {
  runId: string;
  userMessageId: string;
  assistantMessageId: string;
}
```

目标行为：

1. Command 在一个事务中创建用户消息、Run 和助手占位消息。
2. 将活动 Run 注册到 `AppState` 并启动后台任务。
3. 尽快返回 IDs，不等待模型生成结束。
4. 后台任务继续通过当前 Run 的 Channel 发送事件。

### 事件信封

```ts
interface AgentRunEvent<TEvent extends string, TData> {
  schemaVersion: 1;
  eventId: string;
  conversationId: string;
  runId: string;
  sequence: number;
  timestamp: string;
  event: TEvent;
  data: TData;
}
```

规则：

- `sequence` 在单个 Run 中单调递增。
- 前端按 `runId + sequence` 去重，忽略重复或过期事件。
- `eventId` 用于日志关联和后续诊断。
- 事件是实时投影，不作为持久化真相。

### 事件集合

第一阶段实现：

```text
run_started
phase_changed          thinking | responding
output_text_delta
usage_updated
run_completed
run_failed
run_cancelled
```

接入 Tools 时新增：

```text
tool_call_requested
tool_approval_required
tool_call_started
tool_call_completed
tool_call_failed
```

前端不接收 `reasoning_delta`。隐藏推理只用于 Runtime 内部继续模型调用。

### Commands 草案

```text
conversation_create
conversation_list
conversation_find
conversation_update
conversation_delete
conversation_message_list

agent_run_start
agent_run_snapshot
agent_run_cancel

tool_call_decide
```

不要求第一阶段一次实现全部 CRUD；按垂直切片添加实际需要的 Command。

## 6. 前端状态模型

### 持久状态

通过 Commands 和 React Query 管理：

- Conversation 列表。
- 当前 Conversation 的 Message 列表。
- Run 快照和历史状态。

### 活动流状态

通过按 Run 隔离的 reducer 管理：

- 当前 `sequence`。
- 运行阶段。
- 尚未写回查询缓存的文本增量。
- 当前 Tool Call 和审批状态。

Run 完成后重新读取或刷新 Conversation Message，最终以 Rust 返回的持久数据为准。

为了减少 Streamdown 和 React 的重复渲染，文本增量可以按一帧或短时间窗口合并后再更新 UI，不要求每个供应商 Token 都触发一次 React State 更新。

## 7. Agent Runtime 与 Tools

### 供应商无关请求

当前 `CompletionRequest` 后续演进为能够表达完整上下文和工具定义的内部请求：

```text
AgentRequest
  model
  messages
  thinking
  reasoning_effort
  tools
```

内部事件至少能够表达：

```text
ReasoningDelta
TextDelta
ToolCallDelta
Completed
```

### Agent Loop

```text
加载 Conversation 上下文
  → 解析 Skills 和 Tools
  → 调用模型
  → 收集文本、推理或 Tool Call
  → 如有 Tool Call，校验与审批后执行
  → 将 Tool Result 加入上下文
  → 再次调用模型
  → 直到最终文本、取消、错误或达到步骤上限
```

必须设置：

- 最大模型调用次数。
- 最大工具调用次数。
- 单工具超时。
- 取消传播。
- 工具参数 Schema 校验。
- 工具输出大小限制。
- 重复调用检测。

### Tool Registry

每个 Tool 提供：

```text
name
description
input_schema
risk_level
approval_policy
execute
```

Rust 根据风险决定是否需要审批。模型无权自行降低风险或跳过审批。

### 审批交互

需要审批时：

1. Tool Call 持久化为 `waiting_approval`。
2. Run 进入 `waiting_approval`。
3. 前端收到 `tool_approval_required`。
4. 用户通过 `tool_call_decide` 提交允许或拒绝。
5. 决定必须绑定 `runId + toolCallId + 参数摘要`。
6. Rust 再次校验参数和目标状态后执行。

`AppState` 后续增加活动 Run Registry，保存取消令牌和等待审批的通道。该结构只负责运行期句柄，不作为持久状态来源。

## 8. Skills 接入原则

Skill 是 Agent 指令和能力配置，不等同于 Tool。

```text
Skill
  id
  version
  description
  instructions
  resources
  required_tools
```

Run 启动时：

```text
最终指令 = 应用基础指令 + 本次选中的 Skills
最终工具 = 应用允许工具 ∩ Skill 请求工具 ∩ 用户权限
```

初期策略：

- 先支持用户手动选择 Skill。
- 暂不实现自动 Skill 路由。
- Skill 由 Rust 加载和校验，前端只展示可选元数据。
- Skill 不能绕过 Tool Registry、风险等级和审批。
- 接入 Skills 后，在 Run 中记录实际使用的 Skill ID 和版本，便于复现和诊断。

## 9. 隐藏推理处理

- Provider Adapter 继续解析 `reasoning_content`。
- Runtime 可以在当前 Run 内暂存推理内容。
- 前端只看到 `phase_changed: thinking`，不看到推理正文。
- 普通多轮对话不把上一轮隐藏推理加入下一轮上下文。
- DeepSeek 在同一轮 Tool Call 子请求中需要回传的推理内容，由 Runtime 临时保留。
- 第一版不持久化 Chain of Thought；应用退出时不恢复正在进行的推理。
- Usage 中保留供应商提供的总 Token 信息，后续供应商支持时再单独增加 reasoning token 字段。

## 10. 持久化与恢复策略

不为每个文本 Delta 写一次 SQLite。建议：

1. Run 开始时事务创建用户消息、Run 和助手占位消息。
2. 流式文本先在 Runtime 内存累积。
3. 按短时间窗口或字符阈值批量更新助手消息，降低写入频率。
4. Run 完成时事务写入最终文本、状态、用量和结束时间。
5. 失败或取消时保留已生成的部分文本，并记录对应 Message 和 Run 状态。
6. 前端重载后通过 `agent_run_snapshot` 和消息查询恢复，不依赖事件重放。
7. 应用启动时将遗留的 `pending`、`running`、`waiting_approval` Run 标记为中断；真正的跨重启恢复后置。

## 12. 测试与验收重点

### 协议

- [x] Rust 与 TypeScript 字段、枚举和 camelCase 序列化一致。
- [x] Run Event `sequence` 单调且可去重。
- [x] 未知或非法状态转换返回稳定错误。

### 持久化

- [x] 用户消息和 Run 创建保持事务一致性。
- [x] 完成、失败和取消均保存正确的最终状态。
- [x] 应用重启后不会把遗留 Run 错误显示为仍在执行。

### Runtime

- [x] 正常文本流不重复、不丢失最终文本。
- [x] 取消会中止当前模型流。
- [ ] 达到步骤、超时或输出限制后可诊断地终止。
- [x] 隐藏推理不会出现在 IPC、日志或持久消息中。

### Tools 与 Skills

- [ ] 未注册工具不能执行。
- [ ] 参数不符合 Schema 时不能执行。
- [ ] 需要审批的工具在批准前零副作用。
- [ ] Skill 只能使用最终允许集合中的工具。
- [ ] 模型不能通过伪造工具名或结果绕过 Runtime。

## 13. 本计划非目标

- 不在第一阶段实现完整 Tool 或 Skill 框架。
- 不实现任意 Shell、任意脚本或任意应用 UI 自动化。
- 不实现多 Agent。
- 不实现云同步和跨设备 Run。
- 不实现每 Token Event 的数据库事件溯源。
- 不实现应用退出后继续执行或恢复进行中的 Run。
- 不提前抽象附件、Artifact、多模态 Message Part 和长期记忆。

后续只有在对应真实需求进入实施阶段时，才新增具体模块、表和协议字段。
